PART 0

The method

Designing a database for a client does not start by writing CREATE TABLE. It starts three phases earlier. The order matters because each phase produces the input for the next, and skipping one is exactly what produces databases like the one you have today: tables that are correct one by one, inconsistent as a whole.

  1. 0RequirementsInterviews with the client and study of the business. Output: a list of rules in human language, not tables. “A welcome coupon is used only once per customer.” “The delivery address is frozen when payment is made.”Tools: structured interview, event storming, data dictionary.
  2. 1Conceptual modelEntities and relationships, without types or keys. What things exist and how do they relate? It is drawn, shown to the client and corrected on the whiteboard — it is the cheapest phase in which to be wrong.Tools: entity-relationship diagram (crow's foot), entity list.
  3. 2Logical modelPrimary and foreign keys, cardinalities, normalisation up to 3NF, and deliberate denormalisations (in commerce: the order snapshots).Tools: 1NF/2NF/3NF, query-driven design.
  4. 3Physical modelSpecific engine, exact types, CHECK constraints, indexes, sequences, triggers. Here and only here is SQL written.Tools: DDL, index plan, EXPLAIN ANALYZE.
  5. 4Migration and seedsBringing the client's real data into the new schema: profiling, cleaning, loading, verifying counts. Never “I'll move it over by hand”.Tools: data profiling, idempotent scripts, control counts.
  6. 5OperationsTested backups, versioned migrations, slow-query monitoring. A database without a tested restore is not in production, it is at risk.Tools: pg_dump, schema_migrations table, restore drill.

The step 0 rule: an answer you don't know yet is not solved by “leaving it flexible”. It is solved by asking. A “just in case” field is a postponed decision that someone will get wrong six months from now.

From spoken rule to written constraint

This is the central exercise of the method, and the one that separates an amateur database from a professional one. Every sentence from the client must end up as something the database prevents, not something the code remembers to check.

What the client saysWhat gets written
“Emails are never repeated.”email CITEXT UNIQUE NOT NULL
“Nobody rates a product twice.”UNIQUE INDEX (product_id, user_id) WHERE user_id IS NOT NULL
“An order cannot be left without a way to contact the customer.”CHECK (user_id IS NOT NULL OR (email IS NOT NULL AND phone IS NOT NULL))
“The total has to add up.”CHECK (total = subtotal + delivery_fee - discount)
“The order statuses are these five.”CHECK (status IN ('pending','confirmed','shipped','delivered','cancelled'))
“The discount never exceeds the subtotal.”CHECK (discount <= subtotal)

The practical difference: a rule in the code gets skipped if someone writes directly to the database, if two processes run at once, or if another endpoint is added tomorrow. A rule in the database is never skipped.

Two quick readings of this diagram:

  • PRODUCTS, CATEGORIES and BRANDS belong to Directus. Everything else is your own SQL. It is a single database with two owners, and that boundary must be respected in both directions.
  • ORDER_ITEMS hangs off PRODUCTS and PRODUCT_VARIANTS. That double link is what is broken today by a type clash, and it is the reason you cannot tell which size was sold.

The most common conceptual mistake in shops: treating the order as a pointer to the catalogue. An order does not point to a 110-guilder product: it records that on that day it cost 110. If the price goes up and the order reads it by reference, the sales history rewrites itself. Your schema already freezes name, SKU, price, size and colour in order_items — that is done well and should not be touched.

PART 3

Logical model: normalisation, with your data

Normalisation is always explained with toy examples. There is no need here: your catalogue has the three classic violations, and each one produces a symptom you are already seeing.

1NF — one cell, one value

This is how a bra looks today in database/seed-data.json, and how it was loaded into Directus:

// The parent product, exactly as it is today
{
  "ref":   "REF 011473",
  "name":  "Leonisa Bra",
  "price": 110,
  "color": "BEIGE, BLANCO, BERDE, GRIS, NEGRO",   ← five values in one cell
  "size":  "38B, 40 B, 38C, 36B, 36 B, 34 B",      ← six values in one cell
  "stockQuantity": 9
}

A cell holding a list of values breaks first normal form. The consequence is not theoretical:

  • You cannot filter “colour = black” without LIKE '%NEGRO%', which also matches BEIGE ESTAMPADO NEGRO.
  • You cannot count how many products come in beige.
  • stockQuantity: 9 says nothing useful: nine of which size?

The correct form already exists in your schema and is called product_variants: one row per real size and colour combination, each with its own stock and its own SKU. The parent product keeps what is true for all variants (name, brand, description, image) and nothing else.

2NF and 3NF — every piece of data where it belongs

Second normal form: no field depends on only part of the key. Third: no field depends on another field that is not the key. In practice, for a shop, it boils down to one question: does this piece of data change on its own, or does it change because something else changed?

DataWhere it is todayWhere it goesWhy
Brand nameText "Leonisa" repeated on every productbrands.name + products.brand_idIf the name is corrected, it is corrected in one place, not in 133 rows.
Stock for a sizeproducts.stock_quantity and product_variants.stock_quantityOnly on the variant; the product's is calculatedTwo numbers that claim to be the same always end up disagreeing.
Delivery costconstants.js, settings table and Directusdelivery_zonesThree sources, three possible answers to the same question.
Price paidCopied into order_itemsStays thereDenormalisation on purpose: history is not rewritten.

When NOT to normalise. Normalising is the rule; freezing is the exception, and it is deliberate. In an order, the following are frozen: product name, SKU, unit price, size, colour, image and the full delivery address. Everything else is referenced. The test for deciding: if the original data changed tomorrow, should the old document change too? If the answer is no, it gets frozen.

PART 4

Physical model: types, keys and constraints

Now SQL does get written. The decisions in this phase are the hardest to reverse later, so each one has a reason.

Choosing types

ForTypeReason
MoneyDECIMAL(10,2)FLOAT loses cents. In a shop that is an accounting mismatch, not a rounding detail.
Customer or order identifierUUIDDoes not reveal how many customers you have and cannot be guessed from outside.
Product identifierINTEGERImposed by Directus. You don't fight the CMS: you accept it and use the same type in every foreign key.
EmailCITEXTCase-insensitive comparison. Ana@x.com and ana@x.com are the same person.
DatesTIMESTAMPTZAlways with time zone. Curaçao is UTC−4 and the server is in Missouri.
Order addressJSONBIt is a snapshot, not a relationship. Indexable with GIN if it is ever needed.
StatusesVARCHAR + CHECKAdding a status is an ALTER TABLE. With an ENUM type it is a much more awkward operation to reverse.

The order lifecycle

Statuses are not a list of words: they are a machine with permitted transitions. Drawing it is what makes it possible to write the CHECK and to know which transitions the API must reject.

stateDiagram-v2
    [*] --> pending: checkout creates the order
    pending --> confirmed: payment approved
    pending --> cancelled: unpaid / customer cancels
    confirmed --> shipped: out for delivery
    confirmed --> cancelled: voided before dispatch
    shipped --> delivered: handed over
    delivered --> [*]
    cancelled --> [*]
    note right of cancelled
        returns stock
        releases the coupon
    end note

Three concrete things come out of this drawing: the CHECK on orders.status, the rows that order_status_history writes on each arrow, and the rule that delivered and cancelled are terminal — nothing comes back from them.

Indexes: the minimum needed

An index is added when a real query needs it, not “just in case”: every index slows down writes and takes disk space. The ones your shop does need:

-- Lookups by natural key (login, order tracking)
CREATE UNIQUE INDEX ON users (email);
CREATE UNIQUE INDEX ON orders (order_number);

-- Listings: "my orders", newest first
CREATE INDEX ON orders (user_id, created_at DESC);

-- Partial index: only indexes what is queried publicly
CREATE INDEX ON reviews (product_id) WHERE is_approved = TRUE;

-- Business rules that also speed things up
CREATE UNIQUE INDEX ON reviews (product_id, user_id) WHERE user_id IS NOT NULL;
CREATE UNIQUE INDEX ON product_variants (product_id, size, color);

-- Full-text search over the catalogue
CREATE INDEX ON products USING GIN (name gin_trgm_ops);

The two unique indexes above are not optimisations: they are the rules “one review per person and product” and “one variant per size and colour” turned into something the database guarantees even if two requests arrive in the same millisecond.

The SKU problem and the “weird stuff”

You were right. These are the 24 distinct size strings in your data, for what are really about ten sizes:

38B · 40 B · 38C · 36B · 36 B · 34 B · 38 B · 38 C · 368C · 40C
36  B · 38  B · 36 C · 40 C · 40  B · 40  D · 40 D · 34  B · 40B
S · M · L · XL · XXL
  • 38B, 38 B and 38  B are the same size written three ways. To the database they are three different sizes.
  • 368C is a typo nobody caught because the field accepts any text.
  • Bra sizes (34B) and shapewear sizes (S, XL) coexist in the same column. They are two different sizing systems.

And the colours:

BEIGE · BLANCO · BERDE · GRIS · NEGRO · BEIGE  ESTAMPADO · CAFE PRINT
ROJO · BEIGE STAMPADO · ORANGE · BEIBE · DARK RED · MANDARIN
HABANO · ESTAMPADO ROSADO · (empty) · BLACK
  • BERDE is VERDE (green). BEIBE is BEIGE. BEIGE STAMPADO and BEIGE  ESTAMPADO are the same colour, misspelled in two ways.
  • NEGRO and BLACK coexist. So do ROJO, DARK RED and MANDARIN.
  • There is an empty colour: a variant with no colour, which the database accepted without complaint.

The SKUs are BRA-001 to BRA-077, numbered consecutively. They are unique, which is good, but they encode nothing: from the SKU you cannot tell the product, the size or the colour. If tomorrow you insert a bra in the middle, the numbering loses its order.

There is a single root cause: size and colour are free text. A free-text field that is later used to filter, count or group always ends up like this — not through carelessness, but because nothing prevents it. The professional solution is not “be more careful when typing”: it is a controlled vocabulary, a sizes table and a colours table, with the variant pointing to them.

How to fix it

-- Controlled vocabulary: the closed set of valid sizes
CREATE TABLE sizes (
    code        VARCHAR(8) PRIMARY KEY,   -- '38B', 'XL'
    system      VARCHAR(12) NOT NULL       -- 'bra' | 'apparel'
                CHECK (system IN ('bra','apparel')),
    sort_order  INTEGER NOT NULL              -- so that S < M < L in listings
);

CREATE TABLE colors (
    code        VARCHAR(24) PRIMARY KEY,  -- 'BEIGE'
    label_es    VARCHAR(40) NOT NULL,
    hex         CHAR(7)                     -- for the colour picker on the product page
);

-- The variant no longer accepts made-up text
ALTER TABLE product_variants
    ADD CONSTRAINT fk_variant_size  FOREIGN KEY (size)  REFERENCES sizes(code),
    ADD CONSTRAINT fk_variant_color FOREIGN KEY (color) REFERENCES colors(code);

-- Meaningful SKU: brand-reference-size-colour
-- LEO-011473-38B-BEI  instead of  BRA-001

Once that foreign key is in place, BERDE can no longer exist: the database rejects the row. And the frontend's size picker can be populated from the table instead of extracting unique values from free text.

PART 7

Runbook: from step 0 to the final step

The exact steps to get the database into the shape it should be in. Everything is run from Coolify → resource unistyles-postgres → Terminal, unless stated otherwise. The order is non-negotiable: each step assumes the previous one.

STEP 0Back up before touching anything
pg_dump -U unistyles -d unistyles_db -F c -f /tmp/unistyles-$(date +%F).dump
ls -lh /tmp/unistyles-*.dump

If the file does not appear or is only a few kilobytes, stop. Without a verified backup, you do not continue. This is not ceremony: you have already lost this database once in a redeploy.

STEP 1Profile: is there real data to keep?
psql -U unistyles -d unistyles_db -c "select 'users' t,count(*) from users
 union all select 'orders',count(*) from orders

This decides the branch: if everything is zero except products, the path is clean (step 2A). If there are real orders or customers, you must migrate with ALTER and preserve them (step 2B).

PART 8

Operations: how not to end up here again

Versioned migrations

You already have the tool and it is not being used: database/migrate.js keeps a record in the schema_migrations table and applies each file in database/migrations/ exactly once. There are four migrations written and not applied.

database/
  init.sql            ← the schema for a freshly created database. Never edited
                        to fix production.
  migrations/
    001_...sql        ← every later change, numbered, applied once
    005_schema_v2.sql ← the missing one
  migrate.js          ← node database/migrate.js

The five rules that keep a client database healthy

  1. One source per piece of data. If a piece of data can be edited in two places, in three months they will say different things. Today your business configuration lives in three.
  2. Rules go in the database. If the code is the only thing checking them, they are not rules: they are habits.
  3. No free text in anything you filter on. Size, colour, status, payment method: a closed set, always.
  4. History is frozen. Orders, payments and invoices store a copy, not a reference.
  5. Every change is a migration. Never a stray ALTER typed into a terminal that nobody ever looks at again.

What gets added later, without redesigning anything

A good schema lets you grow without surgery. These are additive and can wait: a wishlist in a table instead of localStorage; a returns table when returns stop being exceptional and handled over WhatsApp; a stock movement ledger when “why is this number wrong?” becomes a frequent question; a roles table when a third type of user appears. None of them forces you to touch what came before — and that is precisely the sign that the model is well conceived.

What already exists in the repo and is worth reading alongside this: docs/DATABASE_ARCHITECTURE.md has the complete dictionary of the 15 tables, the commented DDL, the indexing strategy and the map of each backend route to its tables. database/init.v2.sql is the implementation, ready to run and not yet published to GitHub.
