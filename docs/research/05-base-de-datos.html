PARTE 0

El método

Diseñar una base de datos para un cliente no empieza escribiendo CREATE TABLE. Empieza tres fases antes. El orden importa porque cada fase produce el insumo de la siguiente, y saltarse una es exactamente lo que produce bases como la que tienes hoy: tablas correctas una por una, incoherentes en conjunto.

  1. 0RequisitosEntrevistas con el cliente y lectura del negocio. Salida: una lista de reglas en lenguaje humano, no tablas. «Un cupón de bienvenida se usa una sola vez por cliente». «El domicilio se congela cuando se paga».Herramientas: entrevista estructurada, event storming, diccionario de datos.
  2. 1Modelo conceptualEntidades y relaciones, sin tipos ni claves. ¿Qué cosas existen y cómo se relacionan? Se dibuja, se enseña al cliente, se corrige en la pizarra — es la fase más barata de equivocarse.Herramientas: diagrama entidad-relación (pata de gallo), listado de entidades.
  3. 2Modelo lógicoClaves primarias y foráneas, cardinalidades, normalización hasta 3FN, y las desnormalizaciones deliberadas (en comercio: los snapshots del pedido).Herramientas: 1FN/2FN/3FN, diseño dirigido por consultas.
  4. 3Modelo físicoMotor concreto, tipos exactos, restricciones CHECK, índices, secuencias, triggers. Aquí y solo aquí se escribe SQL.Herramientas: DDL, plan de índices, EXPLAIN ANALYZE.
  5. 4Migración y semillasLlevar los datos reales del cliente al esquema nuevo: perfilado, limpieza, carga, verificación de conteos. Nunca «lo paso a mano».Herramientas: perfilado de datos, scripts idempotentes, conteos de control.
  6. 5OperaciónCopias de seguridad probadas, migraciones versionadas, monitorización de consultas lentas. Una base sin restauración probada no está en producción, está en riesgo.Herramientas: pg_dump, tabla schema_migrations, ensayo de restauración.

PARTE 1 · PASO 0

Requisitos: las preguntas que se le hacen al cliente

El paso 0 real. Para Unistyles la clienta eres tú misma, lo cual es más difícil, no más fácil: las reglas que tienes en la cabeza no están escritas en ninguna parte y el código lleva meses adivinándolas.

Las nueve preguntas que definen un comercio electrónico

Pregunta al clienteQué decide en el esquemaRespuesta en Unistyles
¿Se puede comprar sin crear cuenta?Si orders.user_id admite nulo y si hay que guardar contacto suelto.Sí. user_id nulo + CHECK de contacto obligatorio.
¿El mismo artículo se vende en variantes?Si el stock vive en el producto o en la variante. Es la decisión más cara de cambiar después.Sí, brasieres por talla y color. 33 de 285 productos.
¿Qué pasa con el precio si sube mañana?Si el pedido guarda una copia o una referencia.Copia congelada en order_items.
¿Quién puede cambiar el estado de un pedido y queda rastro?Si existe una tabla de historial.Falta. TrackOrder.jsx existe y no tiene nada que mostrar.
¿Un cupón es por persona, por pedido o global?Si hace falta una tabla de canjes.Por persona. Hoy no se controla: WELCOME10 es infinito.
¿Cómo se calcula el envío?Tabla de zonas, o un número quemado en el código.Tres zonas de Curaçao con umbral de envío gratis.
¿Hay impuestos separados en la factura?Si el pedido necesita columnas de impuesto.No. El OB va incluido en el precio de estante.

La regla del paso 0: una respuesta que no sabes todavía no se resuelve «dejándolo flexible». Se resuelve preguntando. Un campo «por si acaso» es una decisión aplazada que alguien tomará mal dentro de seis meses.

De regla hablada a restricción escrita

Este es el ejercicio central del método, y el que separa una base de aficionado de una profesional. Cada frase del cliente tiene que terminar en algo que la base impide, no en algo que el código recuerda comprobar.

Lo que dice el clienteLo que se escribe
«El correo no se repite.»email CITEXT UNIQUE NOT NULL
«Nadie califica un producto dos veces.»UNIQUE INDEX (product_id, user_id) WHERE user_id IS NOT NULL
«Un pedido no puede quedar sin forma de contacto.»CHECK (user_id IS NOT NULL OR (email IS NOT NULL AND phone IS NOT NULL))
«El total tiene que cuadrar.»CHECK (total = subtotal + delivery_fee - discount)
«Los estados del pedido son estos cinco.»CHECK (status IN ('pending','confirmed','shipped','delivered','cancelled'))
«El descuento nunca supera el subtotal.»CHECK (discount <= subtotal)

La diferencia práctica: una regla en el código se salta si alguien escribe directo en la base, si hay dos procesos a la vez, o si mañana se añade otro endpoint. Una regla en la base no se salta nunca.

Dos lecturas rápidas de este diagrama:

  • PRODUCTS, CATEGORIES y BRANDS son de Directus. Todo lo demás es SQL tuyo. Es una sola base con dos dueños, y esa frontera hay que respetarla en los dos sentidos.
  • ORDER_ITEMS cuelga de PRODUCTS y de PRODUCT_VARIANTS. Ese doble vínculo es lo que hoy está roto por un choque de tipos, y es la razón de que no puedas saber qué talla se vendió.

El error conceptual más común en tiendas: tratar el pedido como un puntero al catálogo. Un pedido no apunta a un producto de 110 florines: guarda que ese día costó 110. Si el precio sube y el pedido lo lee por referencia, el histórico de ventas se reescribe solo. Tu esquema ya congela nombre, SKU, precio, talla y color en order_items — eso está bien hecho y no hay que tocarlo.

PARTE 3

Modelo lógico: normalización, con tus datos

La normalización se explica siempre con ejemplos de juguete. Aquí no hace falta: tu catálogo tiene los tres incumplimientos clásicos, y cada uno produce un síntoma que ya estás viendo.

1FN — una celda, un valor

Así está hoy un brasier en database/seed-data.json, y así se cargó a Directus:

// El producto padre, tal cual está hoy
{
  "ref":   "REF 011473",
  "name":  "Leonisa Bra",
  "price": 110,
  "color": "BEIGE, BLANCO, BERDE, GRIS, NEGRO",   ← cinco valores en una celda
  "size":  "38B, 40 B, 38C, 36B, 36 B, 34 B",      ← seis valores en una celda
  "stockQuantity": 9
}

Una celda con lista de valores rompe la primera forma normal. La consecuencia no es teórica:

  • No puedes filtrar «color = negro» sin LIKE '%NEGRO%', que además casa con BEIGE ESTAMPADO NEGRO.
  • No puedes contar cuántos productos hay en beige.
  • stockQuantity: 9 no dice nada útil: ¿nueve de qué talla?

La forma correcta ya existe en tu esquema y se llama product_variants: una fila por combinación real de talla y color, cada una con su propio stock y su propio SKU. El producto padre conserva lo que es verdad para todas las variantes (nombre, marca, descripción, imagen) y nada más.

2FN y 3FN — cada dato donde le toca

Segunda forma normal: ningún campo depende solo de una parte de la clave. Tercera: ningún campo depende de otro campo que no sea la clave. En la práctica, para una tienda, se resume en una pregunta: ¿este dato cambia por su cuenta o cambia porque cambió otro?

DatoDónde está hoyDónde vaPor qué
Nombre de la marcaTexto "Leonisa" repetido en cada productobrands.name + products.brand_idSi se corrige el nombre, se corrige en un sitio y no en 133 filas.
Stock de una tallaproducts.stock_quantity y product_variants.stock_quantitySolo en la variante; el del producto se calculaDos números que dicen ser el mismo siempre acaban discrepando.
Coste del envíoconstants.js, tabla settings y Directusdelivery_zonesTres fuentes, tres respuestas posibles a la misma pregunta.
Precio pagadoCopiado en order_itemsSe queda ahíDesnormalización a propósito: un histórico no se reescribe.

Cuándo NO normalizar. Normalizar es la regla; congelar es la excepción, y es deliberada. En un pedido se congela: nombre del producto, SKU, precio unitario, talla, color, imagen y la dirección completa de entrega. Todo lo demás se referencia. La prueba para decidir: si el dato original cambiara mañana, ¿el documento viejo debería cambiar también? Si la respuesta es no, se congela.

Diseño dirigido por consultas

Antes de dar por bueno un esquema se escriben las preguntas que el negocio va a hacer, y se comprueba que cada una se responde con una consulta razonable. Las tuyas:

Pregunta del negocioHoyCon el esquema v2
¿Cuánto vendí este mes?SíSí
¿Cuántos brasieres beige talla 38B me quedan?No la talla es texto libreSí
¿Qué talla se vende más?No el pedido no guarda la varianteSí
¿Cuándo pasó este pedido a «enviado»?No no hay historialSí
¿Esta clienta ya usó el cupón de bienvenida?NoSí
¿Cuánto descuento regalé con cada código?No se guarda el importe, no el cupónSí
¿Qué productos nunca se han vendido?Frágil sin clave foránea hay huérfanosSí

Cinco de siete preguntas del negocio no tienen respuesta hoy. Eso, y no la estética del SQL, es la medida de si una base está bien diseñada.

PARTE 4

Modelo físico: tipos, claves y restricciones

Ahora sí se escribe SQL. Las decisiones de esta fase son las que más tarde cuesta revertir, así que cada una tiene un motivo.

Elección de tipos

ParaTipoMotivo
DineroDECIMAL(10,2)FLOAT pierde céntimos. En una tienda eso es un descuadre contable, no un redondeo.
Identificador de clienta o pedidoUUIDNo revela cuántas clientas tienes ni se adivina desde fuera.
Identificador de productoINTEGERLo impone Directus. No se pelea con el CMS: se acepta y se usa igual en todas las claves foráneas.
Correo electrónicoCITEXTCompara sin distinguir mayúsculas. Ana@x.com y ana@x.com son la misma persona.
FechasTIMESTAMPTZCon zona horaria siempre. Curaçao es UTC−4 y el servidor está en Misuri.
Dirección del pedidoJSONBEs una foto, no una relación. Indexable con GIN si algún día hace falta.
EstadosVARCHAR + CHECKAñadir un estado es un ALTER TABLE. Con tipo ENUM es una operación mucho más incómoda de revertir.

El ciclo de vida del pedido

Los estados no son una lista de palabras: son una máquina con transiciones permitidas. Dibujarla es lo que permite escribir el CHECK y saber qué transiciones debe rechazar la API.

stateDiagram-v2
    [*] --> pending: checkout crea el pedido
    pending --> confirmed: pago aprobado
    pending --> cancelled: sin pagar / clienta cancela
    confirmed --> shipped: sale a reparto
    confirmed --> cancelled: se anula antes de salir
    shipped --> delivered: entregado en mano
    delivered --> [*]
    cancelled --> [*]
    note right of cancelled
        devuelve stock
        libera el cupón
    end note

De este dibujo salen tres cosas concretas: el CHECK de orders.status, las filas que escribe order_status_history en cada flecha, y la regla de que delivered y cancelled son terminales — nada vuelve de ahí.

Índices: el mínimo que hace falta

Un índice se pone cuando una consulta real lo necesita, no «por si acaso»: cada índice ralentiza las escrituras y ocupa disco. Los que tu tienda sí necesita:

-- Búsquedas por clave natural (login, seguimiento de pedido)
CREATE UNIQUE INDEX ON users (email);
CREATE UNIQUE INDEX ON orders (order_number);

-- Listados: "mis pedidos", de más nuevo a más viejo
CREATE INDEX ON orders (user_id, created_at DESC);

-- Índice parcial: solo indexa lo que se consulta públicamente
CREATE INDEX ON reviews (product_id) WHERE is_approved = TRUE;

-- Reglas de negocio que además aceleran
CREATE UNIQUE INDEX ON reviews (product_id, user_id) WHERE user_id IS NOT NULL;
CREATE UNIQUE INDEX ON product_variants (product_id, size, color);

-- Búsqueda por texto del catálogo
CREATE INDEX ON products USING GIN (name gin_trgm_ops);

Los dos índices únicos de arriba no son optimizaciones: son las reglas «una reseña por persona y producto» y «una variante por talla y color» convertidas en algo que la base garantiza aunque dos peticiones lleguen en el mismo milisegundo.

El problema de los SKU y las «cosas raras»

Tenías razón. Estas son las 24 cadenas distintas de talla que hay en tus datos, para lo que en realidad son unas diez tallas:

38B · 40 B · 38C · 36B · 36 B · 34 B · 38 B · 38 C · 368C · 40C
36  B · 38  B · 36 C · 40 C · 40  B · 40  D · 40 D · 34  B · 40B
S · M · L · XL · XXL
  • 38B, 38 B y 38  B son la misma talla escrita de tres formas. Para la base son tres tallas distintas.
  • 368C es un dedazo que nadie detectó porque el campo admite cualquier texto.
  • Tallas de brasier (34B) y de faja (S, XL) conviven en la misma columna. Son dos sistemas de medida diferentes.

Y los colores:

BEIGE · BLANCO · BERDE · GRIS · NEGRO · BEIGE  ESTAMPADO · CAFE PRINT
ROJO · BEIGE STAMPADO · ORANGE · BEIBE · DARK RED · MANDARIN
HABANO · ESTAMPADO ROSADO · (vacío) · BLACK
  • BERDE es VERDE. BEIBE es BEIGE. BEIGE STAMPADO y BEIGE  ESTAMPADO son el mismo color, escrito mal de dos maneras.
  • NEGRO y BLACK conviven. ROJO, DARK RED y MANDARIN también.
  • Hay un color vacío: una variante sin color, que la base aceptó sin protestar.

Los SKU son BRA-001 a BRA-077, numerados de corrido. Son únicos, eso está bien, pero no codifican nada: por el SKU no se sabe el producto, ni la talla, ni el color. Si mañana insertas un brasier en medio, la numeración deja de tener orden.

La causa raíz es una sola: talla y color son texto libre. Un campo de texto libre que luego se usa para filtrar, contar o agrupar siempre termina así — no por descuido, sino porque nada impide lo contrario. La solución profesional no es «tener más cuidado al escribir»: es un vocabulario controlado, una tabla de tallas y una de colores, y que la variante apunte a ellas.

Cómo se arregla

-- Vocabulario controlado: el conjunto cerrado de tallas válidas
CREATE TABLE sizes (
    code        VARCHAR(8) PRIMARY KEY,   -- '38B', 'XL'
    system      VARCHAR(12) NOT NULL       -- 'bra' | 'apparel'
                CHECK (system IN ('bra','apparel')),
    sort_order  INTEGER NOT NULL              -- para que S < M < L en los listados
);

CREATE TABLE colors (
    code        VARCHAR(24) PRIMARY KEY,  -- 'BEIGE'
    label_es    VARCHAR(40) NOT NULL,
    hex         CHAR(7)                     -- para el selector de color de la ficha
);

-- La variante ya no admite texto inventado
ALTER TABLE product_variants
    ADD CONSTRAINT fk_variant_size  FOREIGN KEY (size)  REFERENCES sizes(code),
    ADD CONSTRAINT fk_variant_color FOREIGN KEY (color) REFERENCES colors(code);

-- SKU con significado: marca-referencia-talla-color
-- LEO-011473-38B-BEI  en vez de  BRA-001

A partir de esa clave foránea, BERDE deja de poder existir: la base rechaza la fila. Y el selector de tallas del frontend se puede poblar desde la tabla en vez de sacar valores únicos de un texto libre.

Los defectos estructurales

Estos ya estaban documentados en docs/DATABASE_ARCHITECTURE.md y siguen vivos en producción. Los seis que rompen algo hoy:

#DefectoQué se rompe

El catálogo vive en cuatro sitios

Esta es la otra mitad del problema, y la que te afecta cada vez que quieres quitar o añadir un producto.

Regla para el día a día: productos, categorías y marcas se editan solo en cms.unistylescuracao.com. Nunca con SQL, nunca en productData.js. El archivo local es solo la red de seguridad para cuando el CMS no responde, y hay que regenerarlo desde Directus, no editarlo a mano.

PARTE 6

Frontend → backend → base de datos

Una base de datos no se diseña en el vacío: se diseña contra los caminos que la aplicación recorre. Estos son los tuyos, reales, sacados del código.

Quién habla con quién

DatoEl navegador lo pide aQue lo lee de
Catálogo, categorías, marcas, páginasDirectus directamente directusService.jsproducts, categories, brands
Registro, sesión, perfilAPI Express utils/api.jsusers, addresses + Redis
CarritoAPI Express cartService.jscarts con sesión, Redis si es invitada
Pedido, pago, seguimientoAPI Expressorders, order_items, payments

La frontera es limpia y conviene mantenerla así: el contenido lo sirve el CMS, el dinero lo sirve la API. Nada que mueva dinero pasa por Directus, y el navegador nunca escribe en el catálogo.

Dos cosas de este diagrama ya están bien resueltas en tu código y merece la pena que las reconozcas, porque son precisamente las que se suelen hacer mal: el bloqueo FOR UPDATE antes de descontar stock, y que el webhook de pago no se crea nunca a ciegas sino que se vuelve a preguntar al proveedor. Lo que falta es lo de alrededor: el registro del canje del cupón y la fila de historial de estado.

PARTE 7

Runbook: del paso 0 al paso final

Los pasos exactos para dejar la base como debe estar. Todo se ejecuta desde Coolify → recurso unistyles-postgres → Terminal, salvo donde se diga otra cosa. El orden no es negociable: cada paso asume el anterior.

PASO 0Copia de seguridad antes de tocar nada
pg_dump -U unistyles -d unistyles_db -F c -f /tmp/unistyles-$(date +%F).dump
ls -lh /tmp/unistyles-*.dump

Si el archivo no aparece o pesa unos pocos kilobytes, detente. Sin copia verificada no se sigue. Esto no es ceremonia: ya perdiste esta base una vez en un redespliegue.

PASO 1Perfilar: ¿hay datos reales que conservar?
psql -U unistyles -d unistyles_db -c "select 'users' t,count(*) from users
 union all select 'orders',count(*) from orders
 union all select 'order_items',count(*) from order_items
 union all select 'payments',count(*) from payments
 union all select 'reviews',count(*) from reviews
 union all select 'product_variants',count(*) from product_variants
 union all select 'products',count(*) from products order by 1"

Decide la rama: si todo está en cero menos products, el camino es limpio (paso 2A). Si hay pedidos o clientas reales, hay que migrar con ALTER y conservar (paso 2B).

PASO 2ABase vacía — recrear con el esquema v2

PARTE 8

Operación: cómo no volver aquí

Migraciones versionadas

Ya tienes la herramienta y no se está usando: database/migrate.js lleva un registro en la tabla schema_migrations y aplica una sola vez cada archivo de database/migrations/. Hay cuatro migraciones escritas y sin aplicar.

database/
  init.sql            ← el esquema de una base recién creada. No se edita jamás
                        para arreglar producción.
  migrations/
    001_...sql        ← cada cambio posterior, numerado, aplicado una vez
    005_schema_v2.sql ← el que falta
  migrate.js          ← node database/migrate.js

Las cinco reglas que mantienen sana una base de cliente

  1. Una fuente por dato. Si un dato se puede editar en dos sitios, dentro de tres meses dirán cosas distintas. Hoy tu configuración del negocio vive en tres.
  2. Las reglas van en la base. Si el código es el único que las comprueba, no son reglas: son costumbres.
  3. Nada de texto libre en lo que se filtra. Talla, color, estado, método de pago: conjunto cerrado, siempre.
  4. El histórico se congela. Pedidos, pagos y facturas guardan copia, no referencia.
  5. Cada cambio es una migración. Nunca un ALTER suelto escrito en una terminal que nadie vuelve a ver.

Qué se añade más tarde, sin rediseñar nada

Un buen esquema deja crecer sin cirugía. Estas son aditivas y pueden esperar: lista de deseos en tabla en vez de localStorage; tabla de devoluciones cuando dejen de ser excepcionales y por WhatsApp; libro mayor de movimientos de stock cuando «¿por qué este número está mal?» se vuelva frecuente; tabla de roles cuando aparezca un tercer tipo de usuario. Ninguna obliga a tocar lo anterior — esa es justamente la señal de que el modelo está bien planteado.

Lo que ya existe en el repo y conviene leer junto a esto: docs/DATABASE_ARCHITECTURE.md tiene el diccionario completo de las 15 tablas, el DDL comentado, la estrategia de índices y el mapa de cada ruta del backend a sus tablas. database/init.v2.sql es la implementación, lista para ejecutar y todavía sin publicar a GitHub.
